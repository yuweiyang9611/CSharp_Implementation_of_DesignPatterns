# C# 设计模式实战项目学习指南

这份指南先把 GoF 23 种模式放进三个可以直接运行的 .NET 10 教学项目，再用两个高级实验连接安全重构和生产可靠性。目标不是记住 23 张类图，而是练习四个更重要的问题：变化发生在哪里、对象边界怎样划分、多个模式怎样协作，以及怎样用测试证明系统在修改或故障后仍然正确。

> 先把项目当作业务系统运行，再把它当作模式教材阅读。只看类名很容易学成“模式识别题”，从业务变化反推设计才接近真实开发。

## 1. 三个项目覆盖全部 GoF 23 种模式

| 分类 | 模式 | 主教学项目 | 它解决的业务变化 |
| --- | --- | --- | --- |
| 创建型 | Abstract Factory | DocumentWorkflow | 一次切换整套兼容的 Web 或 Print 发布组件 |
| 创建型 | Builder | OnlineStore | 分步骤收集订单资料，并保证订单创建时合法 |
| 创建型 | Factory Method | OnlineStore | 新增支付通道时不修改结算主流程 |
| 创建型 | Prototype | DocumentWorkflow | 从审批过的报表模板复制新实例 |
| 创建型 | Singleton | SmartHome | 教学性地维护进程内唯一设备类型注册表，并讨论代价 |
| 结构型 | Adapter | SmartHome | 把旧空调的厂商接口转换为统一设备协议 |
| 结构型 | Bridge | SmartHome | 设备类型和通信通道两个维度独立扩展 |
| 结构型 | Composite | SmartHome | 对单个设备、房间和楼层执行一致操作 |
| 结构型 | Decorator | DocumentWorkflow | 按部署配置叠加水印、签名或审计能力 |
| 结构型 | Facade | OnlineStore | 为一次结算用例提供稳定入口 |
| 结构型 | Flyweight | DocumentWorkflow | 在大量文档元素之间共享不可变样式 |
| 结构型 | Proxy | SmartHome | 不改变设备接口地加入授权和访问审计 |
| 行为型 | Chain of Responsibility | OnlineStore | 让订单规则按顺序校验并能独立增删 |
| 行为型 | Command | SmartHome | 把设备操作变成可排队、记录和撤销的对象 |
| 行为型 | Interpreter | DocumentWorkflow | 用小型筛选语言选择需要发布的章节 |
| 行为型 | Iterator | DocumentWorkflow | 隐藏章节集合内部结构并按业务顺序遍历 |
| 行为型 | Mediator | SmartHome | 让传感器和设备通过家庭中枢联动 |
| 行为型 | Memento | SmartHome | 保存并恢复家庭场景，而不暴露内部状态 |
| 行为型 | Observer | OnlineStore | 订单事件发生后通知库存、邮件和审计订阅者 |
| 行为型 | State | OnlineStore | 让订单在不同状态下拥有不同合法操作 |
| 行为型 | Strategy | OnlineStore | 在运行时切换标准或 VIP 定价算法 |
| 行为型 | Template Method | DocumentWorkflow | 固定发布骨架，只允许子类替换少量步骤 |
| 行为型 | Visitor | DocumentWorkflow | 在稳定文档结构上增加统计和合规操作 |

这里的“覆盖”不是在输出中打印模式名称，而是让每个模式承担一个可观察的业务职责。删除某个模式后，相应变化会重新散落到调用方或条件分支中。

## 2. 项目一：OnlineStore 电商结算系统

### 2.1 业务故事

顾客提交购物车后，系统需要构建订单、检查资料和库存、计算价格、选择支付通道、推进订单状态，并通知库存、邮件和审计模块。每一步都会变化，但结算用例对客户端应保持稳定。

一条典型成功路径是：

```text
客户端
  -> Checkout Facade
     -> Validation Chain
     -> Pricing Strategy
     -> Order Builder
     -> Payment Factory Method
     -> Order State transition
     -> Order Event Publisher
        -> Inventory subscriber
        -> Email subscriber
        -> Audit subscriber
```

### 2.2 七个模式怎样协作

| 模式 | 在项目中的职责 | 观察点 |
| --- | --- | --- |
| Builder | 收集顾客、商品、地址等字段后创建合法订单 | 必填字段缺失时，错误集中在构建边界暴露 |
| Chain of Responsibility | 依次执行资料、库存、金额或风险规则 | 任一规则拒绝时，后续规则和支付不会执行 |
| Strategy | 计算标准或 VIP 商品价格 | 更换策略不会修改订单实体和结算外观 |
| Factory Method | 由支付服务的具体实现创建处理器 | 增加新通道时，结算流程只依赖抽象 |
| State | 控制待支付、已支付、已发货、已完成等状态的合法动作 | 非法转换会被当前状态对象拒绝 |
| Observer | 将订单事件分发给多个独立副作用处理器 | 新增订阅者不需要改订单状态逻辑 |
| Facade | 把完整结算流程收敛为一个用例级入口 | 场景入口不需要知道每个子系统的调用顺序 |

### 2.3 为什么不是一个巨大的 CheckoutService

最初版本完全可以写成一个服务，但它通常会快速出现以下信号：

- `if` 或 `switch` 同时决定折扣、支付、配送和状态；
- 校验规则既修改订单又发送邮件；
- 新增支付通道必须修改结算主函数；
- 状态字段可以被任意代码赋值；
- 单元测试只能从头运行整条流程。

Facade 仍然负责用例编排，但把可替换算法、生命周期规则和副作用边界交给更小的对象。这里的重点是“职责分离”，不是让 Facade 变成另一个上帝类。

### 2.4 推荐阅读顺序

1. 从 `Program.cs` 进入 `OnlineStoreSystem.Create`，找到结算用例的对象装配。
2. 阅读 Facade 的公开方法，写下稳定步骤和可能失败点。
3. 进入 Builder 和校验链，观察非法订单在哪一层被拒绝。
4. 比较两个 Strategy 或支付实现，确认调用方依赖的是抽象。
5. 沿订单成功事件追踪 Observer，区分领域状态变化和外部副作用。
6. 最后阅读 State，列出所有允许和禁止的转换。

### 2.5 渐进练习

#### 练习 A：增加会员定价

新增一个会员策略：金卡会员享受商品小计折扣，但运费不参与折扣。要求不修改订单实体，也不在 Facade 中增加会员等级分支。

验收重点：策略只接收完成计算所需的数据；金额使用 `decimal`；测试覆盖普通会员和金卡会员。

#### 练习 B：增加“货到付款”

货到付款不立即扣款，但仍要产生支付受理结果。思考它是新的 Factory Method 产品、支付策略，还是新的订单状态。先写业务语义，再决定模式。

#### 练习 C：可恢复的事件订阅

让邮件订阅者模拟失败，保证库存处理结果不会被回滚。进一步讨论真实生产系统为什么会使用 Outbox，而不是让内存 Observer 承担可靠消息职责。

#### 练习 D：退货流程

扩展订单状态图，加入 `ReturnRequested`、`Returned` 和 `Refunded`。不要让客户端直接修改状态；为每个非法转换写测试。

### 2.6 容易学错的地方

- Builder 不等于给所有属性加链式 setter；它必须保护复杂对象的构建规则。
- Strategy 不应直接访问整个服务容器；依赖越多，算法越难独立替换。
- Observer 只负责通知，不自动提供持久化、重试和消息顺序保证。
- Facade 简化入口，但不应吞掉所有领域错误。
- State 的价值在于行为随状态变化；只有一个枚举字段时未必需要状态对象。

## 3. 项目二：SmartHome 智能家居系统

### 3.1 业务故事

家庭中有新旧厂商设备、不同通信协议、房间和楼层分组，以及需要权限控制的远程访问。住户希望执行“离家”命令、撤销误操作，并在烟雾或门窗事件发生时由中枢协调多个设备。

```text
用户命令 -> 授权代理 -> 设备抽象 -> 通信通道
                       |
传感器事件 -> 家庭中枢 +-> 分组设备
                       +-> 场景快照与恢复
```

### 3.2 八个模式怎样协作

| 模式 | 在项目中的职责 | 变化被隔离在哪里 |
| --- | --- | --- |
| Singleton | 提供唯一设备类型注册表 | 进程级类型元数据的唯一性 |
| Adapter | 包装旧厂商空调接口 | 厂商方法名、单位和返回值差异 |
| Bridge | 分开设备抽象与通信实现 | 新设备类型和新协议不再产生笛卡尔积子类 |
| Composite | 把设备、房间、楼层组织成树 | 调用方对叶子与容器使用统一控制接口 |
| Proxy | 在设备前加入授权和审计 | 访问策略不侵入真实设备 |
| Command | 封装开关、调温和场景动作 | 请求可以记录、排队和撤销 |
| Mediator | 根据传感器事件协调设备 | 设备不互相持有引用形成网状依赖 |
| Memento | 保存并恢复场景状态 | 快照不暴露设备集合的内部表示 |

### 3.3 Adapter 与 Bridge 为什么同时出现

两者看起来都在“连接接口”，但方向不同：

- Adapter 面向一个已经存在且无法修改的接口，目标是让它符合当前系统协议。
- Bridge 在设计阶段主动分离两个会独立变化的维度，例如设备能力和通信通道。

旧空调适配完成后，可以像其他设备一样参与 Composite、Proxy 和 Command；它仍直连旧厂商 API。Bridge 则用于原生灯具和警报器，把设备类型与通信通道分开。Adapter 位于遗留系统边界，Bridge 位于新设备的内部抽象结构。

### 3.4 Proxy、Command 与权限边界

远程用户执行命令时，Command 表达“想做什么”，Proxy 判断“能不能做”，真实设备负责“怎样做”。三者顺序很重要：

```text
Command.Execute
  -> AuthorizedDeviceProxy
     -> policy check
     -> audit
     -> RealDevice
```

如果把权限判断写进每个命令，新设备命令会复制安全规则；如果写进设备本体，本地自动化和远程访问就无法采用不同策略。

### 3.5 Singleton 的教学警告

注册表使用 Singleton 是为了展示进程内唯一入口，但真实项目优先考虑由依赖注入容器管理单实例生命周期。全局可访问的 Singleton 会隐藏依赖、污染测试，并让并发初始化更难推理。

学习时做一次替换实验：把注册表改为普通对象，由 `Program.cs` 创建并注入。若业务代码几乎不需要修改，说明抽象边界合理；若很多类直接访问 `.Instance`，说明全局耦合已经扩散。

### 3.6 推荐阅读顺序

1. 从通信实现和设备抽象理解 Bridge 的两个维度。
2. 阅读旧空调 Adapter，确认单位转换和接口语义都被隔离。
3. 查看 Composite 如何递归控制房间或楼层。
4. 从命令入口追踪 Proxy 到真实设备，观察授权失败路径。
5. 执行命令并撤销，检查 Command 保存的最小恢复信息。
6. 触发传感器事件，查看 Mediator 怎样协调多个同事对象。
7. 保存场景、修改设备、再由 Memento 恢复。
8. 最后审视 Singleton 是否能被注入式单例替代。

### 3.7 渐进练习

#### 练习 A：增加 Bluetooth Mesh 通道

只增加一个通信实现，让现有原生灯具和警报器都可选择 Bluetooth Mesh。若需要为每种设备复制类，说明 Bridge 边界没有真正分开。旧空调仍通过 Adapter 访问遗留 API，不强行接入 Bridge。

#### 练习 B：访客权限

访客可以开客厅灯，但不能查看摄像头或执行全屋离家场景。把策略注入 Proxy，并记录允许与拒绝的审计结果。

#### 练习 C：宏命令与事务边界

创建“夜间模式”宏命令。第三个设备执行失败时，是否撤销前两个动作？比较尽力而为、补偿动作和真正事务三种语义。

#### 练习 D：场景快照版本

设备固件升级后状态格式发生变化。为 Memento 增加版本，并在恢复时处理缺失设备和旧字段。

### 3.8 容易学错的地方

- Composite 的统一接口不代表叶子必须支持容器的所有管理操作。
- Proxy 与 Decorator 结构相似，但 Proxy 的重点是访问路径和生命周期控制。
- Command 的撤销不是简单执行相反命令；它通常要保存执行前状态。
- Mediator 不应演变成知道所有业务细节的超级控制器。
- Memento 保存的是恢复所需状态，不是随意公开对象内部字段。

## 4. 项目三：DocumentWorkflow 文档发布系统

### 4.1 业务故事

企业从审批过的报表模板创建季度报告，根据筛选表达式选择章节，执行统计和合规检查，然后发布 Web 版或打印版。发布过程还可能叠加水印、签名和审计，且大量段落共享相同样式。

```text
Approved Template --clone--> Report instance
      -> filter expression
      -> ordered section traversal
      -> metric/compliance visitors
      -> publication template
         -> Web component family OR Print component family
         -> decorators
```

### 4.2 八个模式怎样协作

| 模式 | 在项目中的职责 | 判断它有价值的信号 |
| --- | --- | --- |
| Prototype | 复制审批过的模板 | 创建成本高，且新文档大部分结构相同 |
| Interpreter | 解析并执行章节筛选规则 | 规则组合由用户或配置决定，语法范围有限 |
| Iterator | 按业务顺序遍历章节 | 调用方不应依赖集合实现或树结构 |
| Visitor | 对章节执行统计与合规操作 | 文档元素类型稳定，而操作经常增加 |
| Flyweight | 共享不可变排版样式 | 文档元素数量大且重复样式占用明显 |
| Abstract Factory | 创建兼容的 Web/Print 组件族 | 一次切换必须保证整套产品互相匹配 |
| Template Method | 固定加载、检查、渲染、发布的骨架 | 流程顺序稳定，少数步骤因渠道变化 |
| Decorator | 按配置叠加水印、签名和审计 | 职责可独立组合，组合顺序有语义 |

### 4.3 创建模式的组合顺序

Prototype 和 Abstract Factory 都在创建对象，但创建知识不同：

- Prototype 从一个已配置且已审批的实例复制内容结构。
- Abstract Factory 根据目标渠道创建一整套兼容发布组件。

先克隆业务文档，再选择发布产品族，可以让“报告内容”和“渠道实现”保持独立。不要用一个巨大工厂同时复制模板、解析筛选条件并执行发布。

### 4.4 Interpreter 的适用边界

项目中的筛选语言故意保持很小：有限字段、明确运算符、可组合表达式。Interpreter 适合教学和受控领域语言，不适合重新实现 SQL、正则表达式或通用脚本引擎。

增加语法前先回答：

1. 规则是否真的需要由运行时文本配置？
2. 一个委托或 Specification 对象是否已经足够？
3. 输入是否可信，复杂度是否有上限？
4. 错误位置和错误消息怎样反馈给用户？

### 4.5 Decorator 顺序为什么重要

假设原始内容依次经过水印和签名：

```text
Sign(Watermark(Content))
Watermark(Sign(Content))
```

两者可能产生不同结果。签名通常应覆盖最终内容，因此装饰器的装配顺序是业务规则，不只是技术细节。测试应断言最终行为和顺序，而不是断言创建了多少层包装类。

### 4.6 推荐阅读顺序

1. 从报告模板和克隆行为理解 Prototype 的深浅复制边界。
2. 查看章节集合的 Iterator，确认调用者不知道内部存储结构。
3. 沿筛选表达式树理解 Interpreter 的组合规则。
4. 对同一报告执行两个 Visitor，比较新增操作和新增元素类型的成本。
5. 检查 Flyweight 的共享状态是否真正不可变。
6. 比较 Web 与 Print 两套 Abstract Factory 产品是否保持兼容。
7. 阅读 Template Method 的固定骨架和受保护扩展点。
8. 最后改变 Decorator 装配顺序，观察输出差异。

### 4.7 渐进练习

#### 练习 A：增加移动端产品族

增加 Mobile 工厂及其兼容组件，不修改客户端发布流程。若客户端要分别判断主题、导航和渲染器类型，说明产品族抽象不完整。

#### 练习 B：组合筛选语法

在现有括号、`AND`、`OR`、`NOT` 和 `pages >= n` 基础上，增加带引号的标题匹配或 `pages <= n`，并继续为非法 token、缺失右括号和未知字段提供定位清楚的错误。

#### 练习 C：隐私 Visitor

新增一个操作，收集包含个人信息的章节并生成审计报告。不要修改已有章节类，比较 Visitor 与在每个元素上增加方法的取舍。

#### 练习 D：样式缓存边界

统计创建 10,000 个段落时 Flyweight 工厂的唯一实例数。随后把一个可变字段放进共享样式，观察跨段落污染，理解内在状态必须不可变的原因。

### 4.8 容易学错的地方

- Prototype 必须明确深复制和共享引用；调用 `MemberwiseClone` 不等于完成设计。
- Abstract Factory 保证产品族兼容，不是所有 `new` 的统一出口。
- Flyweight 的外在状态应由调用方传入，不能悄悄写回共享对象。
- Visitor 适合元素类型稳定的结构；元素类型频繁增加时维护成本会反转。
- Template Method 的扩展点越多，流程约束越弱，最后可能退化为脆弱基类。

## 5. 跨项目比较：相似模式怎样选

### 5.1 Facade 与 Mediator

| 问题 | Facade | Mediator |
| --- | --- | --- |
| 主要目的 | 给复杂子系统提供更简单的外部入口 | 协调一组同事对象之间的交互 |
| 典型方向 | 客户端单向调用子系统 | 同事把事件交给中介者，中介者再协调其他同事 |
| 本项目 | OnlineStore 的结算入口 | SmartHome 的传感器联动中枢 |
| 风险 | Facade 变成上帝服务 | Mediator 变成集中式业务泥团 |

### 5.2 Adapter、Bridge、Decorator 与 Proxy

它们都可能表现为“包装一个对象”，但意图不同：

- Adapter 改变接口，让旧对象能接入新系统。
- Bridge 主动拆分两个独立变化的抽象维度。
- Decorator 保持接口并按需叠加职责。
- Proxy 保持接口并控制访问、位置或生命周期。

判断顺序是：先说清楚变化，再看结构。只因为代码中有一个包装字段，不能反推出模式。

### 5.3 State、Strategy 与 Command

- Strategy 由调用方或配置选择“采用哪种算法”。
- State 由对象当前生命周期决定“现在允许怎样行为”。
- Command 把“这次请求”本身对象化，以便记录、排队、重试或撤销。

一个智能家居命令可以调用策略，也可以改变设备状态；三者是不同维度，不必互相替代。

### 5.4 Builder、Factory Method、Abstract Factory 与 Prototype

| 你真正要变化的内容 | 优先考虑 |
| --- | --- |
| 复杂对象需要分步收集数据并在完成时校验 | Builder |
| 基类流程要把一个产品的创建交给具体实现 | Factory Method |
| 必须一次创建一整套互相兼容的产品 | Abstract Factory |
| 已有一个配置完整的实例，创建新对象主要靠复制 | Prototype |

## 6. 怎样测试模式组合

### 6.1 测业务轨迹，不测类图

有效测试应回答：

- 校验失败后是否停止支付？
- 非法状态转换是否被拒绝？
- 命令撤销后是否恢复执行前状态？
- 权限拒绝时真实设备是否完全没有收到调用？
- 筛选表达式是否选中正确章节？
- 装饰器顺序是否产生期望的最终结果？

不要把“实现了某个接口”“对象是某个具体类型”当作主要行为测试。重构实现结构时，这类测试会产生大量无业务价值的失败。

### 6.2 为什么项目提供 `--self-test`

三个项目不依赖外部测试框架，因此在离线环境也能运行。自检使用固定数据验证关键结果，适合教材、CI 烟雾验证和读者快速确认环境。

```powershell
dotnet run --project examples/OnlineStore -- --self-test
dotnet run --project examples/SmartHome -- --self-test
dotnet run --project examples/DocumentWorkflow -- --self-test
```

仓库已经提供 `tests/TeachingProjects.Tests` 正式 xUnit 行为测试，并保留 `--self-test` 作为零依赖教学入口。扩展练习应先在正式测试项目中写出失败用例，再实现并重构；涉及数据库、网络和时钟时还要建立可替换边界。

### 6.3 组合模式最需要的测试

1. 成功路径：确认模式组合后的整体业务结果。
2. 短路路径：责任链、授权代理和校验失败后不应继续产生副作用。
3. 顺序路径：装饰器、模板步骤和事件处理顺序需要明确语义时必须测试。
4. 恢复路径：Command 撤销和 Memento 恢复应验证执行前后状态。
5. 扩展路径：新增一个策略、产品或访问者时，旧场景仍通过且修改面可控。

## 7. 三个可选扩展方向

### 7.1 电商售后与退款

在 OnlineStore 上增加退货、退款、补偿和客服审批。重点练习 State、Chain of Responsibility、Command 与 Observer 的边界，讨论跨服务事务为什么不能靠内存对象解决。

### 7.2 家庭能源优化

在 SmartHome 上增加实时电价、光伏发电和电池储能。用 Strategy 表达调度算法，用 Observer 接收价格变化，再评估是否需要引入事件总线，而不是继续膨胀 Mediator。

### 7.3 多租户文档平台

在 DocumentWorkflow 上增加租户主题、权限、发布队列和版本历史。重点处理 Abstract Factory 的产品族范围、Proxy 的租户隔离、Prototype 的模板版本以及 Decorator 的装配配置。

## 8. 四周学习计划

### 第 1 周：跑通业务并识别变化

- 每天运行一个项目场景并手绘业务时序。

### 第 2 周：删除模式做对照实验

- 给撤销、恢复和非法状态转换增加测试。

### 第 4 周：完成一个教学项目扩展

- 先写一页设计说明，包含目标、非目标和验收场景。

- 回顾哪些模式可以被更简单的 C# 特性替代。

## 9. 两个高级实验：从重构证据到故障不变量

完成三个教学项目后，再进入 [`labs`](../labs/README.md)。这两个实验不是第四、第五个“模式展示项目”，而是两次能力升级。

### 9.1 CheckoutRefactoringKata：4～7 天安全重构

[Starter](../labs/CheckoutRefactoringKata/Starter/CheckoutService.cs) 的结账行为正确，但校验、计价、状态和外部协作混在一个服务里。不要一次性用 Reference 覆盖它，应按下面路线推进：

```text
坏代码
  -> 特征测试锁定已有输出、副作用和校验顺序
  -> Strategy 隔离价格政策
  -> Chain of Responsibility 组织校验与短路
  -> State 拒绝非法生命周期转换
  -> Facade 为 CLI/HTTP 等调用方提供稳定入口
  -> 等价性测试比较重构前后的收据、失败信息和轨迹
```

运行基线：

```powershell
dotnet test labs/CheckoutRefactoringKata/Tests/CheckoutRefactoringKata.Tests.csproj -c Release
dotnet run --project labs/CheckoutRefactoringKata/Starter/CheckoutRefactoringKata.Starter.csproj -c Release -- success
dotnet run --project labs/CheckoutRefactoringKata/Reference/CheckoutRefactoringKata.Reference.csproj -c Release -- success
```

每个阶段都按“红—绿—重构”推进。特征测试保护调用方已经依赖的行为；等价性测试把同一请求和同一支付响应交给两个实现，证明结构改变没有造成行为漂移。详细步骤、阶段验收、反思题和“何时不该用模式”见 [重构工坊讲义](../labs/CheckoutRefactoringKata/README.md)。

### 9.2 ReliableCheckout：2～3 周生产化毕业路线

[ReliableCheckout](../labs/ReliableCheckout/README.md) 使用 ASP.NET Core Minimal API、SQLite、Transactional Outbox、后台重试、幂等消费者、支付 Adapter、显式状态机、可控时钟和确定性故障注入。建议按下列节奏完成：

| 周次 | 主题 | 必须回答的问题 |
| --- | --- | --- |
| 第 1 周 | HTTP、幂等与原子库存 | 客户端重试为什么不重复扣库存？两个买家为什么不会同时买走最后一件商品？ |
| 第 2 周 | Outbox、退避与恢复 | 数据库已提交但进程退出时支付请求为什么不会丢？handler 重放为什么不二次支付？ |
| 第 3 周（推荐） | 回调、状态机与生产差距 | 重复/乱序回调为什么不能让 `Paid` 倒退？上线前还缺哪些安全与运维能力？ |

运行和测试：

```powershell
dotnet restore labs/ReliableCheckout/ReliableCheckout.slnx
dotnet test labs/ReliableCheckout/ReliableCheckout.slnx -c Release
dotnet run --project labs/ReliableCheckout/ReliableCheckout.Api --urls http://localhost:5188
```

毕业验收不是“找到 Adapter、State、Facade”，而是让以下五个场景全部通过：

1. **重复提交：** 同一 Idempotency-Key 和请求体返回原订单，只扣一次库存；相同 Key 搭配不同请求发生冲突。
2. **并发抢购：** 两个真实 HTTP 请求争抢最后一件库存，恰好一个成功，库存永不为负。
3. **重复与乱序回调：** 早到、重复、成功后又到达的失败回调得到稳定结果，订单不会非法前进或倒退。
4. **Outbox 首次失败恢复：** 首次投递被确定性故障打断，记录尝试；推进 `ManualClock` 后重试成功。
5. **处理后崩溃重放：** handler 已完成但 Outbox 标记前发生故障，重放不会创建第二次支付请求。

模式在这里负责表达职责和合法协作；SQLite 事务、条件更新、幂等收据和 Outbox 负责保护故障下的结果。不要用 GoF 名称掩盖并发、持久化和交付语义。

## 10. 最后的设计复盘清单

完成扩展后，逐项回答：

- 客户端是否依赖稳定抽象，而不是具体实现细节？
- 新增一种变化主要新增文件，还是大量修改旧分支？
- 模式角色是否对应真实业务职责？
- 错误和取消是否沿调用链清楚传播？
- 是否存在隐藏全局状态或不受控的 Singleton 访问？
- 组合顺序是否有业务语义并被测试？
- 能否删除一个抽象而让设计更简单？
- README、运行命令和实际代码是否保持一致？

设计模式不是完成度徽章。最好的结果不是“系统里用了 23 个模式”，而是面对具体变化时，你能解释为什么采用某个结构、它保护了什么边界，以及什么时候应该把它删掉。
