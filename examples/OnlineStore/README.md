# OnlineStore：用真实下单流程学习 7 种设计模式

这是一个可独立运行的 .NET 10 控制台教学项目。它没有把每种模式拆成互不相关的玩具，而是让它们共同完成一次真实的电商下单：购物车校验、VIP 计价、订单组装、钱包支付、库存预留、发货和确认收货。

项目不使用第三方 NuGet 包，开启了 Nullable 与“警告视为错误”。默认场景使用固定商品、价格、库存、订单号和支付结果，因此每次运行都能得到确定、便于对照的执行轨迹。

## 业务故事

VIP 客户“林晓”购买一本《C# 设计模式实战》和两个 C# 马克杯：

1. 结账入口先检查购物车、客户、地址和库存；任一规则失败就停止。
2. 系统根据 VIP 身份选择九折计价，计算商品小计、优惠、运费和应付金额。
3. 订单构建器把客户、地址、商品快照和价格快照组装成订单。
4. 钱包支付创建者生产具体支付处理器并扣款。
5. 订单由“待支付”进入“已支付”；库存、客户通知和审计订阅者收到事件。
6. 仓库发货，客户确认收货；状态对象控制哪些操作在当前阶段合法。
7. `CheckoutFacade` 对调用者隐藏上述协作细节。

## 运行方式

在本目录执行：

```powershell
dotnet run
```

执行内置自检：

```powershell
dotnet run -- --self-test
```

也可以从仓库根目录执行：

```powershell
dotnet run --project examples/OnlineStore/DesignPatterns.TeachingProjects.OnlineStore.csproj
dotnet run --project examples/OnlineStore/DesignPatterns.TeachingProjects.OnlineStore.csproj -- --self-test
```

`--self-test` 覆盖五条路径：完整成功订单、空购物车被校验链拦截、同 SKU 重复加入后按总数量检查库存、负配送费用在计价前被拒绝、余额不足导致订单取消。任一断言失败，进程会返回非零退出码。

## 七种模式如何落到业务中

| 模式 | 主要角色 | 在本项目中的可观察行为 | 合理扩展点 |
| --- | --- | --- | --- |
| Builder | `IOrderBuilder`、`OrderBuilder` | 输出 `[Builder]`，分步收集客户、地址、商品和价格后一次性创建合法订单 | 增加发票、礼品包装、企业采购字段，而不膨胀构造函数 |
| Factory Method | `PaymentProcessorCreator`、`WalletPaymentProcessorCreator` | 输出具体 Creator 创建了哪种 Processor，随后执行真实的余额判断 | 新增银行卡或货到付款 Creator，各自创建对应处理器 |
| Facade | `CheckoutFacade` | 调用者只提交 `CheckoutCommand`，Facade 编排校验、计价、构建、事件和支付 | API、桌面端、批处理都可复用同一结账入口 |
| Chain of Responsibility | `CheckoutValidationRule` 及五个具体规则 | 每条规则输出通过/拒绝；失败立即短路，支付不会发生 | 插入限购、风控、优惠券、配送范围规则 |
| Observer | `OrderEventPublisher` 与三个 Subscriber | 状态变化后，库存、通知、审计各自响应；库存仅在支付成功后扣减 | 增加积分、推荐奖励、消息队列转发订阅者 |
| State | `IOrderState` 与五个状态类 | 待支付→已支付→已发货→已完成；取消订单再发货会抛异常 | 增加退款中、已退款、部分发货状态及合法转换 |
| Strategy | `IPricingStrategy`、标准/VIP 策略 | 输出选中的定价算法及精确价格明细 | 增加大促、会员等级、企业协议价策略 |

## 为什么在这里使用

### Builder

订单包含客户、地址、商品快照和价格快照，字段较多并且存在“一起完整才有意义”的约束。Builder 让编排代码具有业务语言感，也避免不断增加超长构造函数。它真正承担了创建合法订单的职责，而不是仅仅转发参数。

### Factory Method

支付渠道的创建往往包含不同 SDK、凭据和风控配置。上层只执行 `Pay` 模板流程，子类决定实例化哪种 Processor，使新增渠道无需修改结账编排。本例的钱包处理器会真实判断余额并返回批准或拒绝结果。

### Facade

完整结账横跨多个子系统。Facade 提供稳定、窄小的入口，避免 UI 或 API 层了解调用顺序。它也明确了事务边界附近“谁负责协调”。

### Chain of Responsibility

结账规则经常增加、调整顺序或按业务线组合。链让每条规则保持单一职责，并在失败时立即终止昂贵的后续操作。本例可以看到空购物车失败后不会构建订单或发起支付。

### Observer

支付成功后，库存、通知和审计都要响应，但订单不应直接依赖这些服务。发布者只广播领域事件，订阅者各自处理；增加积分订阅者无需修改 `Order`。

### State

订单操作的合法性取决于生命周期阶段。若把规则堆成大量 `if (Status == ...)`，很快会失控。状态对象把该阶段允许的操作和转换收拢在一起；例如 Cancelled 状态天然拒绝发货。

### Strategy

标准客户和 VIP 客户的计价算法不同，但输入、输出一致。Strategy 允许运行时替换算法，并让每种算法能独立测试。促销策略增加时，结账流程不需要知道折扣细节。

## 什么时候不要使用

- 订单只有两个必填字段且永远不会增长时，直接构造比 Builder 更清楚。
- 系统只有一个固定支付实现、也不需要隔离创建细节时，Factory Method 会增加无谓层级。
- 调用方本来就需要细粒度控制各步骤时，不应强迫它经过 Facade。
- 校验只有一两个稳定条件时，普通函数顺序调用比责任链更直接。
- 只有一个固定后续动作时，直接调用通常比维护订阅关系更容易追踪。
- 生命周期只有两个状态且转换规则简单时，枚举加少量条件可能足够。
- 永远只有一种定价公式时，不必预先创建 Strategy 接口。

判断标准不是“能不能套模式”，而是变化方向是否真实存在，以及模式减少的耦合是否大于它增加的间接性。

## 推荐阅读顺序

1. 从 `Application/DemoScenario.cs` 看业务输入和最终结果。
2. 阅读 `Application/CheckoutFacade.cs`，先理解总流程。
3. 顺着输出标签依次阅读 `Validation`、`Pricing`、`Building`、`Payments`。
4. 阅读 `Domain/Order.cs`、`States` 和 `Events`，观察状态转换如何触发订阅者。
5. 最后阅读 `Application/SelfTestRunner.cs`，理解如何用行为而不是类名验证模式。

## 练习题

1. 新增“满 300 减 40”定价策略，并明确它与 VIP 折扣是否叠加。为 299、300、500 三个边界金额写自检。
2. 新增 `BankCardPaymentProcessorCreator`，模拟卡号末位为偶数时批准；不要修改 `CheckoutFacade` 的支付流程。
3. 在责任链中插入“单 SKU 最多购买 5 件”规则，并验证失败后没有创建订单。
4. 新增积分订阅者：订单完成后按实付金额累计积分。证明取消订单不会增加积分。
5. 增加 `Refunding` 与 `Refunded` 状态，定义 Paid、Shipped 两种状态下不同的退款规则。
6. 给 Builder 增加可选发票信息，并保证未提供发票时现有调用代码不变。
7. 模拟库存订阅者抛出异常，思考同步 Observer 的失败会如何影响订单；再设计 Outbox/消息队列版本。
8. 当前库存校验和扣减之间可能发生并发竞争。尝试用带版本号的库存预留结果修复，并解释模式之外还需要哪些一致性机制。

## 项目边界

这是教学项目，因此支付、库存和通知都在进程内运行，订单号生成器也使用固定前缀。真实生产系统还需要数据库事务、幂等键、并发库存控制、支付回调验签、敏感数据保护、可靠消息和可观测性。这些工程问题不能只靠设计模式解决，但本项目留下的接口和协作边界可以作为继续演进的起点。
